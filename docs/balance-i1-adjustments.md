# IDR adjustment request boundary (#543)

I1 implements the service and database seam for [issue #543](https://github.com/Alhiefikri/telegram-bot/issues/543), using the accepted [H0-v1 single-Owner overlay / ADR-0020](https://github.com/Alhiefikri/telegram-bot/blob/9dbbaa80/docs/adr/0020-single-owner-balance-adjustments.md). Dependencies A0 #537 and R1 #541 are closed. I2 #544 adds the owner-only Dashboard adapter; full reversal remains I3 #545. No deployment, production activation or USDT funding is authorized by I1.

`BalanceAdjustmentService::request()` requires the authenticated current Owner and a started session. It looks up an existing Customer by a canonical positive numeric Telegram-ID string. Unknown IDs never create Customers. Positive IDR units accept integers or canonical integer strings, reject floats and ambiguous formats, and remain bounded by the signed BIGINT/PHP integer representation. There is no business maximum. The immutable preview contains the stored Customer identity, Owner, session/credential bindings, category, optional original source/verified receipt fingerprint, reason, IDR amount, version 1, server-generated UUID nonce and five-minute expiry. A request writes no ledger or receipt claim.

`confirm()` requires that exact request/fingerprint/version and a fresh password on every call, including replay. `ApprovedBalanceAdjustment` can only be minted from the successful request-bound password lease. The canonical ledger accepts this typed authority plus a transaction-approved persisted request; it does not expose a new arbitrary credit method. Matching replay returns the original posting, including after preview expiry; terminal rejection/cancellation/expiry cannot post. Changed bindings, a different Owner, revoked access, a password rotation or a new session require a new preview. No password/hash credential is serialized into request, audit, job or notification records; previews store an irreversible credential-version digest.

The password boundary rejects caller-owned transactions, so failed attempts cannot disappear with money rollback. PostgreSQL stores the per-Owner sliding 15-minute failure window, a 30-second verification lease and a successful request/fingerprint binding. Only one KDF verification runs per Owner at once; contenders receive `confirmation_busy`. Five failures lock the Owner for 15 minutes, with one audit and one durable outbound alert per episode. Timestamp expiry is request-driven; there is no per-actor scheduler. Successful verification is consumed inside the posting transaction and the lease is released on failed posting. Process loss leaves an expiring lease; Redis loss cannot reset failures. I3 reversal must reuse this boundary, including its lockout, rather than introducing another password endpoint.

For a new manual credit the lock order is User (shared authority) → auth state → Customer → IDR account → request → receipt, if any. Existing Top-up recovery continues Customer/account → Top-up/compensation; registered refund recovery continues account → Order/Payments → existing Supplier/SKU/Product resource union → unit/claim/refund. KDF and external I/O stay outside retried money transactions. The outer transaction retries deadlocks at most five times.

Categories have distinct economic meaning:

- `owner_attested` is the default unrecorded case, requiring a reason without payment proof. Its counterpart is `owner_attested_adjustment_suspense` against `customer_idr_liability`; it never fabricates an external receipt or verified asset. Independently submitted unlinked requests cannot prove physical-money uniqueness, as accepted in H0-v1.
- `funded_transfer` requires a qualified `VerifiedMoneyReceipt`, exact IDR amount/zero decimals, and verified Customer attribution supplied by the trusted verifier. The service binds the observation to the new adjustment target and claims it globally at posting. Held outcomes commit review/reservation evidence without credit. Public screenshots/hashes do not constitute this typed verification. No new provider verifier or public receipt-input endpoint is introduced.
- `promotional_grant` and `correction` have explicit expense/suspense counterparts; they are service categories, not additional Dashboard defaults.
- `top_up_recovery` binds the original Customer and amount and calls the existing Top-up-specific compensation owner. Settlement and compensation still share their original resolution and receipt reservation. Trusted late provider evidence/callbacks claim the original Top-up receipt before releasing that reservation; they never credit the compensated source again. The existing Customer compensation notification is materialized inside the adjustment transaction, and the later compensation event reuses it. An already resolved original cannot receive another independent adjustment.
- `refund_recovery` binds a registered requested IDR warranty/missing-unit entitlement, verifies the original paid Payment and Customer, and completes that same refund/claim/fulfillment. Uncertain external transfers, already resolved refunds, non-IDR payments, unsupported remainder cases and unverified entitlements fail closed. The credit uses `order_refund` and its existing idempotency key; internal balance refunds retain the original-debit cap. Customer refund selection must already be registered; I1 does not infer it from an Owner's free-text reason.

Posting commits request resolution, canonical ledger/projection, one balanced accounting counterpart, audit and Customer/Owner Telegram obligations together. The additive tables have restrictive financial foreign keys and unique posting identities. PostgreSQL protects request identity/terminal history, accounting, adjustment entries and adjustment audit rows against UPDATE/DELETE; model guards also protect request identity. Legacy IDR entry amounts/kinds and other writer ownership remain unchanged. Projection drift and integer overflow reject the whole posting.

Notifications materialize through `TelegramOutboundEffectService`, use the sole ledger protocol, and are picked up by the existing `telegram:recover-outbound` scheduler and dispatcher. Delivery ambiguity enters the existing manual-review flow; delivery failure never undoes or repeats money. Customer text is localized for id/en/ms. Owner alerts use the existing configured admin Telegram recipient; missing mapping fails confirmation closed. I2 implements the authenticated session/CSRF adapter and approved confirmation flow. The production Owner-to-recipient mapping still needs operational qualification before activation. No new ENV setting is added.

Verification lives at `AdminBalanceAdjustmentTest` and `AdminBalanceAdjustmentPostgresConcurrencyTest`: pending/replay, exact input/identity, role/session/password/version removal, five-failure lockout, cancellation/rejection/expiry, qualified receipt reuse, source recovery, full rollback at accounting/audit/outbound inserts, exact input/overflow/projection drift, notification recovery, immutable PostgreSQL history and process races across original Top-up/refund/receipt resolutions. `AdminBalanceAdjustmentDashboardTest` covers the Owner HTTP flow and fail-closed projection display. SQLite proves behavior only; PostgreSQL evidence is required for locks/constraints. I3/V1 still own reversal behavior and broader crash/operational qualification. Production Owner-to-Telegram recipient mapping remains an activation gate.

## I2 Owner Dashboard adapter (#544)

The Owner-only Admin Dashboard uses `admin.store-balance.adjustments.*` routes. The Owner link and every route stay hidden/blocked until U1's `customer_usdt_balance_accounts`, `customer_usdt_balance_entries`, and `customer_usdt_balance_accounting_events` schemas exist. It searches only by an exact canonical numeric Telegram ID string and calls `BalanceAdjustmentService::request()` for an already registered Customer. Unknown IDs never create a Customer. The page shows current identity and an IDR snapshot verified by `StoreBalanceLedger::snapshot()`, accepts an additional positive integer amount and required reason, then renders the service's immutable five-minute preview. Projection drift hides the amount and disables confirmation. The Owner confirms with a fresh password bound to the request, version, fingerprint, authenticated session and current credential. A repeated confirmation returns honest replay feedback without a second ledger posting. CSRF is included on each mutation form; non-Owners are rejected by route middleware and the service authority check.

The screen deliberately has no payment-proof upload, accounting-category selector or distinct-approver step under H0-v1. It paginates Customer adjustment requests and positive IDR projection accounts; zero-balance accounts stay in the database and are hidden only from the positive-balance list. Adjustment history renders ledger direction when present so a later linked reversal is shown as a debit. The reversal operation and its ledger type remain I3 #545.

U1 #546 is still open and the repository has no Customer USDT Balance account/ledger to query. This I2 implementation therefore tracks the available positive IDR projection only; it does not synthesize or infer USDT balances. Feature and Browser fixtures create empty marker schemas only to exercise the gated IDR flow. Routes stay closed until U1 installs its real account, entry and accounting-event tables. Even after that schema gate opens, #544 remains incomplete until the Dashboard also tracks verified positive USDT balances.
