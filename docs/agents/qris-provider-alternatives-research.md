# QRIS provider alternatives for Lhie Store

> Research note, checked against public first-party sources on 2026-09-08. This is a provider-selection report, not production qualification. Public documentation can differ from the contract, channel set, limits, and pricing enabled for a particular merchant.

## Decision

**Recommended provider: Midtrans Core API QRIS.** Its documented minimum charge does not require buyer identity, its create response provides a ready-to-fetch QR PNG action, and it has signed notifications plus an authoritative status API. Midtrans also publicly permits domestic-individual onboarding, publishes a 0.7% QRIS fee including tax, and documents cancel and QRIS refund operations. These facts make it the best-balanced replacement for a hosted, identity-heavy flow ([QRIS create/response](https://docs.midtrans.com/reference/qris), [optional customer fields](https://docs.midtrans.com/reference/customer-details-object), [notification verification](https://docs.midtrans.com/reference/handle-notifications), [pricing](https://midtrans.com/id/biaya), [onboarding documents](https://docs.midtrans.com/docs/apa-saja-dokumen-legalitas-yang-diperlukan-untuk-registrasi-akun-midtrans)).

The recommendation is conditional on a merchant-sandbox test proving that the enabled QRIS acquirer returns a fetchable `generate-qr-code`/`generate-qr-code-v2` image and that the image remains usable for the chosen order lifetime. Midtrans's official pages do not provide one consistent dynamic-QRIS settlement SLA, so that term must be confirmed in the merchant agreement ([static QRIS says two working days](https://docs.midtrans.com/docs/introduction-to-static-qris), while the [general withdrawal page says at least three business days](https://docs.midtrans.com/docs/when-can-i-withdraw-my-transaction-funds-from-midtrans)).

**Best alternatives:** DOKU Direct QRIS if stronger documented cancel/refund controls justify SNAP integration complexity; Xendit Payments API v3 if Lhie Store is eligible for business onboarding; Brick if quote-only pricing is acceptable; and Espay if its excellent QR response contract outweighs unresolved commercial and onboarding terms.

## Interpretation and evidence rules

- **One-time QRIS** means a transaction-specific, fixed-amount QR intended for one order, not a reusable static/open-amount code.
- **No buyer identity required** means the documented create request can omit buyer name, email, and phone. Merchant onboarding/KYC is separate.
- **Telegram-compatible direct QR** means the API returns a QR image URL, Base64 image, or raw EMV QR string that the bot can render and send. A hosted checkout URL alone does not qualify.
- **Authoritative confirmation** means there is both an asynchronous notification/callback contract and a server-to-server inquiry/status operation. A browser redirect or unsigned callback alone is insufficient for fulfillment.
- Suitability judgments are explicitly described as assessments. Material factual claims link to provider-owned documentation, pricing, onboarding, or terms pages; no secondary-source claims are used.

### Direct acceptance answer

The public create contracts support a one-time QRIS payment **without fabricated buyer phone/email/name** for **Midtrans Core API, DOKU Direct, Xendit Payments API v3 `PAY`, Brick Dynamic QRIS, and Espay SNAP QRIS**. Pakasir's example body also omits identity, but its public docs do not formally state field requiredness. **Duitku direct and Tripay Closed do not qualify** because each requires buyer email and name. Tripay Open Payment is not a one-time fixed-amount substitute and Open QRIS availability is unverified.

All five formally identity-free candidates return direct QR material. Midtrans returns a ready image URL; Espay returns an image URL, Base64 image, and raw string; DOKU, Xendit, and Brick return raw strings for local rendering. Pakasir also returns a raw QR string. None of the reviewed direct QRIS create contracts guarantees a QRIS mobile deeplink, so same-device payment from a QR displayed inside Telegram still needs product testing.

## Detailed provider evidence

### Midtrans Core API QRIS

- **Create and identity:** `POST /v2/charge` with `payment_type: "qris"` and `transaction_details.order_id`/`gross_amount`. `customer_details` is optional, and `first_name`, `last_name`, `email`, and `phone` are individually optional ([QRIS](https://docs.midtrans.com/reference/qris), [transaction details](https://docs.midtrans.com/reference/transaction-details-object), [customer details](https://docs.midtrans.com/reference/customer-details-object)).
- **Presentation:** successful creation returns `actions[]` containing GET URLs named `generate-qr-code` and `generate-qr-code-v2`; the latter includes the ASPI border. A separate official POS guide shows raw `qr_string` too ([QRIS response](https://docs.midtrans.com/reference/qris), [POS integration](https://docs.midtrans.com/docs/gopay-qris-pos-integration)). Because the endpoint reference does not show `qr_string`, use the PNG action as the common documented contract and sandbox-qualify raw-string availability.
- **Status/webhook:** QRIS states are `pending`, `settlement`, `expire`, and `deny`; cancellation can add `cancel` ([QRIS](https://docs.midtrans.com/reference/qris), [cancel](https://docs.midtrans.com/reference/cancel-transaction)). Notifications are SHA-512 signed, may duplicate or arrive out of order, and should be challenged against the status API before fulfillment ([notifications](https://docs.midtrans.com/reference/handle-notifications), [status](https://docs.midtrans.com/reference/get-transaction-status)).
- **Expiry:** GoPay Dynamic QRIS defaults to 15 minutes with a 20-second minimum and seven-day maximum. `custom_expiry` supplies order time, duration, and unit; the POS guide advises cancel/expire for precise short lifetimes ([GoPay](https://docs.midtrans.com/reference/gopay), [custom expiry](https://docs.midtrans.com/reference/custom-expiry-object), [POS guide](https://docs.midtrans.com/docs/gopay-qris-pos-integration)). ShopeePay QRIS limits should be confirmed for the enabled acquirer.
- **Cancel/refund:** pending transactions have a cancel endpoint. Settled QRIS can use the refund endpoint, subject to activation and acquirer/issuer windows; documented GoPay QRIS windows are 45 days on-us and seven days off-us ([cancel](https://docs.midtrans.com/reference/cancel-transaction), [refund](https://docs.midtrans.com/reference/refund-transaction)).
- **Assessment:** strongest overall fit. It combines formally optional buyer identity, a ready image action, signed webhook/status verification, individual onboarding, public pricing, and documented lifecycle operations.

### Xendit Payments API v3

- **Current create contract:** new work should use `POST /v3/payment_requests`, `api-version: 2024-11-11`. Dynamic one-time QRIS maps to `type: PAY`, `country: ID`, `currency: IDR`, `request_amount`, and `channel_code: QRIS`; legacy `/qr_codes` `DYNAMIC` maps to this flow ([migration](https://docs.xendit.co/docs/migrate-direct-per-channel-apis-to-v3), [create](https://docs.xendit.co/apidocs/create-payment-request)).
- **Identity:** `customer` and `customer_id` are optional for ordinary `PAY`. They are required for `PAY_AND_SAVE` in specified cases, which is not the intended one-time flow ([create OpenAPI](https://docs.xendit.co/apidocs/create-payment-request)).
- **Presentation:** response `actions[]` supports `PRESENT_TO_CUSTOMER`/`QR_STRING`. The generic response model establishes the action shape, while the QRIS product page identifies QRIS as a present-to-customer QR channel; no QRIS PNG or deeplink is promised ([create](https://docs.xendit.co/apidocs/create-payment-request), [QRIS](https://docs.xendit.co/docs/qris)).
- **Status/webhook:** use `payment.capture` with `data.status: SUCCEEDED`, `payment.failure`, and `payment_request.expiry`; verify `x-callback-token`, deduplicate, and tolerate retries/out-of-order delivery. Inquiry exists for Payment Request and Payment resources ([webhook](https://docs.xendit.co/apidocs/payment-webhook-notification), [handling](https://docs.xendit.co/docs/handling-webhooks), [get request](https://docs.xendit.co/apidocs/get-payment-request), [get payment](https://docs.xendit.co/apidocs/get-payment)).
- **Expiry/cancel/refund:** QRIS defaults to 48 hours and supports configured expiry. Payment Requests can be cancelled before completion. QRIS supports full/partial/multiple partial refunds within the documented seven-day nominal validity, subject to issuer limitations ([QRIS](https://docs.xendit.co/docs/qris), [cancel](https://docs.xendit.co/apidocs/cancel-payment-request), [refund](https://docs.xendit.co/apidocs/refund-payment-request)).
- **Assessment:** strong mature alternative with clean T+1 evidence, but not first choice if Lhie Store is a standalone individual, and a QR rendering step is mandatory.

### Tripay

- **Models:** Closed Payment fixes the amount and creates a one-use code; Open Payment lets the buyer choose amount and reuses a payment code ([developer guide](https://tripay.co.id/developer)). The store-order fit of Closed Payment is an assessment based on those documented properties.
- **Closed create/identity:** `POST /api/transaction/create` requires method, merchant reference, amount, `customer_name`, `customer_email`, item details, and signature; phone is conditional. Callback URL, return URL, and expiry are optional ([developer guide](https://tripay.co.id/developer)). A bot cannot meet this contract without collecting real identity or using undocumented placeholders.
- **Presentation:** current QRIS variants are direct channels. The generic response includes `qr_string`, `qr_url`, and `checkout_url`, but its BRIVA example has null QR fields; a QRIS-specific non-null fixture remains unverified ([channel/create sections](https://tripay.co.id/developer)).
- **Status/webhook/expiry:** raw-body HMAC callback documents `PAID`, `FAILED`, `EXPIRED`, and `REFUND`, with two-minute retries up to three times; detail inquiry is available. QRIS variants have ten-minute minimum expiry and channel-specific maxima of 60 or 1,440 minutes ([developer guide](https://tripay.co.id/developer)).
- **Open Payment limitation:** it relaxes identity, but is not fixed-amount/one-use. The Open API has no documented sandbox and the current channel table does not identify an Open QRIS method ([developer guide](https://tripay.co.id/developer)).
- **Cancel/refund:** no merchant QRIS cancel/refund endpoint is public. Terms discuss disputed refunds and a merchant refund process specifically for cards, so QRIS self-service refund must not be inferred ([terms](https://tripay.co.id/page/terms-and-conditions)).
- **Assessment:** disqualified by mandatory email/name in the correct one-time flow and comparatively high fee/slow clearing.

### Duitku direct v2 and POP

- **Direct create/identity:** `POST /webapi/api/merchant/v2/inquiry` requires buyer `email` and `customerVaName`; phone is optional. Current QRIS codes include ShopeePay, Nobu, Gudang Voucher, and Nusapay ([API v2](https://docs.duitku.com/api/en/)).
- **Presentation:** response provides raw `qrString`, which the merchant renders, and hosted `paymentUrl` ([API response](https://docs.duitku.com/api/en/)).
- **Hosted alternative:** Duitku POP returns a hosted URL and still requires email; it is useful for web but does not remove the identity constraint or return direct QR material in create ([POP](https://docs.duitku.com/pop/en/)).
- **Status/webhook:** direct callback is form-urlencoded and HMAC-signed; status inquiry is available and should be used for confirmation ([API v2 callback/status](https://docs.duitku.com/api/en/)). Callback retry policy is not public.
- **Expiry:** generic QRIS defaults to ten minutes/max 60, while Nobu QRIS defaults to 24 minutes/max 1,440 ([expiry table](https://docs.duitku.com/api/en/)).
- **Cancel/refund:** redirect can report canceled, but no merchant cancellation endpoint is documented. Duitku's pricing FAQ says it does not provide transaction refunds; the merchant handles refunding the buyer ([API](https://docs.duitku.com/api/en/), [pricing FAQ](https://www.duitku.com/harga/)).
- **Assessment:** otherwise credible and inexpensive, but disqualified by mandatory buyer email/name.

### DOKU Direct SNAP QRIS

- **Create:** `POST /snap-adapter/b2b/v1.0/qr/qr-mpm-generate`; required body fields are partner reference, amount/currency, approved `merchantId`, `terminalId`, and `additionalInfo.postalCode`/`feeType`. Required headers include partner/external IDs, timestamp/signature, bearer token, and `CHANNEL-ID: H2H` ([Generate QRIS](https://developers.doku.com/accept-payments/direct-api/snap/integration-guide/qris)).
- **Identity/presentation:** no name/email/phone appears in the create schema. The response returns raw `qrContent`, not an image. The required postal code is described as user postal-code address; whether a stable merchant/store postal code is valid must be confirmed rather than fabricated per order ([Generate QRIS](https://developers.doku.com/accept-payments/direct-api/snap/integration-guide/qris)).
- **Status/webhook:** Query QRIS returns status, paid time, amount, fee, and references. QRIS webhook URL is configured in the DOKU Dashboard ([query](https://developers.doku.com/accept-payments/direct-api/snap/integration-guide/qris#id-2.-query-qris), [webhook setup](https://docs.doku.com/get-started/manage-business/set-up-integration/webhook-payment-notification)). The current QRIS notification sample is on a “Non SNAP” page although its payload identifies SNAP/Direct; exact headers, acknowledgement, and retries require merchant confirmation.
- **Expiry:** optional ISO-8601 `validityPeriod`; omission defaults to 30 days, which is generally too long for inventory reservation ([Generate QRIS](https://developers.doku.com/accept-payments/direct-api/snap/integration-guide/qris)).
- **Cancel/refund:** `/qr/qr-expire` invalidates an unpaid QR by moving expiry to current time. `/qr/qr-mpm-refund` handles prior successful payments, subject to issuer support ([Direct QRIS operations](https://developers.doku.com/accept-payments/direct-api/snap/integration-guide/qris), [issuer support](https://docs.doku.com/accept-payments/no-integration-products/qris#refund-via-direct-api)).
- **Assessment:** best lifecycle-control alternative for an Indonesian individual or company able to implement SNAP safely; below Midtrans because it needs local rendering and callback clarification.

### Pakasir

- **Create/presentation:** `POST /api/transactioncreate/qris` documents only `project`, `order_id`, `amount`, and `api_key`; response returns fee/total, raw QR `payment_number`, and exact `expired_at`. Pakasir tells merchants to generate the image themselves ([docs](https://pakasir.com/p/docs)). There is no formal schema, idempotency rule, duplicate-order behavior, or amount-validation table.
- **Status/security:** successful payment posts a webhook with no documented signature. Pakasir explicitly tells merchants to validate amount/order and recommends `GET /api/transactiondetail` for a more valid status check ([docs](https://pakasir.com/p/docs)). The status call places the API key in the query string, which can expose it in access logs.
- **Expiry/cancel/refund:** expiry is returned but no default/configuration is public. `/api/transactioncancel` exists, but eligibility and state transition are unspecified. No public refund API/policy was found ([docs](https://pakasir.com/p/docs), [terms](https://pakasir.com/p/tos)).
- **Counterparty/onboarding:** Pakasir states that it is not itself a payment gateway and uses an unnamed gateway to hold/process funds. Public pages claim activation in 1–3 days but do not identify that gateway or publish KYC documents ([homepage/FAQ](https://pakasir.com/)).
- **Assessment:** easiest option, but not the recommended load-bearing replacement until webhook authentication, underlying gateway identity, refund procedure, expiry, cancellation, and KYC are contractually resolved. Always verify a webhook through Transaction Detail before fulfillment.

## Stronger additional candidates discovered

### Brick Dynamic QRIS

- `POST /v2/payments/acceptance/1.0/qr/qr-mpm-generate` has no buyer identity and returns mandatory `qrContent` ([create](https://docs.onebrick.io/brickcollect-acceptance/qris/snap/generate-dynamic-qris-snap), [OpenAPI](https://onebrick.readme.io/reference/generate-dynamic-qris-snap)).
- Brick posts status-change callbacks and exposes a status API with amount and lifecycle states; retries require idempotency ([callback](https://onebrick.readme.io/reference/qris-callback-dynamic-qris), [status](https://docs.onebrick.io/brickcollect-acceptance/qris/snap/dynamic-qris-status-snap)). Callback authentication was not established by the reviewed QRIS page.
- Expiry is configurable from 600 to 86,400 seconds. The guide states a 24-hour default while the older OpenAPI marks the field required; use the returned expiry and sandbox-test validation ([create](https://docs.onebrick.io/brickcollect-acceptance/qris/snap/generate-dynamic-qris-snap)).
- Standard settlement is typically T+1 and eligible merchants can contract for same-day settlement. API pricing is custom. Inquiry recognizes refunded/canceled states, but no public initiation endpoint was found ([settlement](https://www.onebrick.io/same-day-settlement), [pricing](https://www.onebrick.io/pricing), [status](https://docs.onebrick.io/brickcollect-acceptance/qris/snap/dynamic-qris-status-snap)).

### Espay SNAP QRIS

- `POST /api/v1.0/qr/qr-mpm-generate` requires partner reference, merchant ID, amount/currency, and product code; buyer identity is absent. It returns `qrUrl`, `qrContent`, and Base64 `qrImage` ([QRIS API](https://docs.espay.id/pembayaran/direct-api/snap/qris/en/)).
- Merchant must expose Espay-accessible Inquiry and Payment services; inaccessible Inquiry can stop create. Payment callback has a five-second timeout, and an optional status inquiry supports latest/history modes ([integration](https://docs.espay.id/pembayaran/direct-api/snap/qris/en/), [payment](https://docs.espay.id/api-mandatory/snap/payment/en/), [status](https://docs.espay.id/api-opsional/snap/inquiry-status/en/)).
- Default expiry is ten minutes; sandbox has QRIS simulation; minimum amount is Rp10,000 ([QRIS FAQ](https://docs.espay.id/pembayaran/direct-api/snap/qris/en/), [sandbox](https://docs.espay.id/pg/portal-sandbox/en/)). An optional QR refund endpoint exists for completed payments ([refund](https://docs.espay.id/api-opsional/snap/refund-qr/en)).
- Public fee, settlement SLA, accepted entity types, and KYB documents were not found on the official pages reviewed. Those omissions keep Espay below the mature named shortlist despite the best direct QR output.

## Ranked shortlist

1. **Midtrans Core API QRIS — recommended.** Best combination of identity-free create, ready PNG, signed webhook/status, sandbox, public fee, individual onboarding, and lifecycle operations. Remaining gate: dynamic-QRIS settlement and enabled-acquirer sandbox behavior.
2. **DOKU Direct SNAP QRIS.** Strong documented cancel/refund model and Indonesian individual onboarding; lower rank because of SNAP complexity, local rendering, required postal code, and callback-document ambiguity.
3. **Xendit Payments API v3.** Strong webhook/reconciliation/refund model and clear T+1 settlement; lower rank for standalone-individual restrictions and local rendering.
4. **Brick Dynamic QRIS.** Clean identity-free API and clear settlement options; lower rank because pricing is custom and public QRIS cancel/refund initiation is absent.
5. **Espay SNAP QRIS.** Best response payload for Telegram and explicit refund; lower rank because fee, settlement, and KYB are not public and merchant-side services add work.
6. **Pakasir.** Simple and identity-free in examples, but weaker public security/compliance/refund contracts and intermediary status outweigh convenience.

Duitku and Tripay are not shortlisted because their correct direct, fixed-amount create flows require buyer identity fields.

## Evidence gaps and due-diligence questions

### Cross-provider

1. No reviewed direct QRIS response guarantees a QRIS deeplink. Test same-device payment from Telegram, including issuer apps that cannot scan an on-screen QR from the gallery.
2. Public headline fees do not establish negotiated rates, reserves, minimum volume, refund/dispute fees, withdrawal fees, or future regulatory changes. Obtain a written merchant quotation.
3. Test duplicate create/reference behavior, create-timeout recovery, webhook duplication/out-of-order delivery, status consistency, amount/currency integrity, expiry, and cancellation/refund in the actual merchant sandbox.
4. Confirm that the QR payload or image URL remains valid for the locally advertised deadline and that the provider image host permits Telegram's servers to fetch it.

### Provider-specific

- **Midtrans:** dynamic-QRIS settlement, enabled acquirer, raw `qr_string` availability if desired, image URL lifetime, ShopeePay expiry limits, and refund activation.
- **DOKU:** valid source for required postal code, exact SNAP QRIS callback headers/body/acknowledgement/retries, and settlement for the chosen individual/corporate scheme.
- **Xendit:** Indonesian business-document matrix, QRIS-specific v3 validation/min-max expiry, and a real QRIS action fixture. The generic OpenAPI formally marks fewer root fields than the QRIS migration example uses.
- **Tripay:** QRIS-specific non-null `qr_string`/`qr_url`, channel-specific phone requirements, exact KYC documents, and QRIS cancel/refund. Do not assume Open QRIS exists.
- **Duitku:** exact KYC documents, QRIS fund-availability timing, callback retry policy, and refund responsibility. The status page's content type and examples are inconsistent; sandbox-confirm accepted encoding.
- **Pakasir:** underlying licensed gateway identity, KYC/entity rules, signed webhook/source authentication, retry/idempotency, expiry/cancel behavior, refund, withdrawal conditions, and duplicate-order semantics.
- **Brick:** QRIS price, callback authentication, exact expiry validation, and merchant-initiated cancel/refund procedure.
- **Espay:** fee, settlement SLA, entity/KYB list, callback authentication, and confirmation that the generic status endpoint reconciles QRIS by the documented identifiers.

## Recommended qualification path

Use **Midtrans Core API**, not hosted checkout. In sandbox, create a fixed-amount QRIS charge with only `payment_type` and `transaction_details`, deliberately omitting `customer_details`. Verify that the response contains a usable PNG action; present it in Telegram and the storefront; complete payment through the sandbox simulator; accept fulfillment only after signature validation and an authoritative status read reports settlement; then exercise expiry, duplicate notification, cancellation, and an enabled refund path. The cited APIs support this path ([QRIS](https://docs.midtrans.com/reference/qris), [sandbox](https://docs.midtrans.com/docs/testing-payment-on-sandbox), [notifications](https://docs.midtrans.com/reference/handle-notifications), [status](https://docs.midtrans.com/reference/get-transaction-status), [cancel](https://docs.midtrans.com/reference/cancel-transaction), [refund](https://docs.midtrans.com/reference/refund-transaction)).

Do not approve production solely from documentation. The final gate is a written Midtrans commercial response for dynamic-QRIS settlement/fees and one redacted merchant-sandbox evidence set proving identity-free create, Telegram-fetchable presentation, signed notification, matching amount/status inquiry, expiry, and refund/cancel behavior.
