# Taste

## Domain and data modelling
- Represents money/state domains as an append-only immutable ledger plus an atomically maintained projection, with a per-source idempotency key and an immutable economic source identity, so replays return the existing result instead of a second effect. Confidence: 0.75
- Treats one service as the sole seam allowed to mutate such state; models elsewhere must not write the balance directly (projection column deliberately not mass assignable). Confidence: 0.7
- Enforces invariants in the database as the final guard — PostgreSQL check constraints (non-negative balance/amount, positive amount) and unique indexes over idempotency/source claims — not only in application code. Confidence: 0.7
- Prefers fail-safe behaviour over fabricated data: when a projection cannot be reconciled with its source of truth, render an explicit localized "unavailable" state rather than a number. Confidence: 0.65
- Keeps automated reconciliation/checking read-only and advisory (a `store-balance:check`-style command that reports mismatches and exits non-zero); never silently repairs state — a repair must be its own explicit, idempotent, audited operation. Confidence: 0.65

## Code and testing conventions (Laravel/PHP)
- Writes `final` classes with constructor property promotion, explicit return types, enums that carry their own behaviour (`direction()`, `isCredit()`), and model guards that throw on update/delete of immutable rows. Confidence: 0.6
- Tests new concurrency-sensitive behaviour with process-level races (pcntl fork, ready/start markers, result files) behind a dedicated group whose harness refuses to run unless it connects to an isolated test database (`DB_CONNECTION=pgsql`, database name must match test, not production). Confidence: 0.65
- Covers database constraints in tests too: assert that raw inserts violate the expected named constraint. Confidence: 0.55
- Wants implementations and fixes to follow established best practices and be grounded in official library documentation — explicitly asks the agent to "refer context7" (the context7 MCP) for framework/API behaviour instead of ad-hoc patching ("pastikan best practice dan refer context7"), and repeats this ask when greenlighting new feature work ("pastikan best practice dan refer context7" reappears as the condition on a one-line "eksekusi rekomendasimu" go-ahead). Confidence: 0.75
- Expects a fixed defect to be locked down by exhaustive regression coverage of every condition, not just the reproduced case: a data-provider matrix over all relevant provider/system response variants (key missing/nulled/aliased, zero, contradictory aliases, negative/fractional values, HTTP failures, expired/success states, pre-fix stuck rows) plus end-to-end assertions on the money path, justified as preventing recurrence in production. Confidence: 0.75
- Treats non-functional correctness as part of feature sign-off: even after accepting a feature as working ("oke mantap dah bagus"), he asks for one more pass over race conditions, performance issues and N+1 queries ("pastikan sekali lagi mengenai race condition, performance issue, atau N+1 query"). Expect an evidence-backed audit — read-only/transaction-scoped behaviour, index usage, query counts that do not grow with item count, loop-free call paths — rather than verbal reassurance, and permanent guard tests (e.g. query-count assertions) to lock it in. Confidence: 0.7

## Production debugging / auditing
- Treats a repeating operational alarm as a defect in the tooling itself: an alert that keeps firing for one unchanged condition ("readinessnya muncul looping gini") counts as a bug to root-cause, not background noise — expect the alert path to be deduplicated per distinct problem (per-fingerprint cache key, persistent cache store, not a short cooldown) and the genuinely recurring residue distinguished from a real loop (per-run job log lines, always-on dashboard badge). Confidence: 0.5
- Diagnoses production-only incidents against live evidence, but strictly read-only: he explicitly asks for a read-only production audit over SSH (host identity/time, deployed commit and working-tree state, memory/disk capacity, running containers, failed units, bounded log windows) and expects nothing on the production host or its data to be changed. He repeats the request when his own change on production did not produce the expected effect ("saya udah set address saya di production tapi masih muncul begitu" → "biar lebih pasti periksa production"), so a mismatch between local analysis and the observed production behaviour must be resolved against the live host — expect the real root cause (e.g. an env key that is absent/never updated on the VPS, a stale container or release state) rather than a restatement of the local findings. Confidence: 0.65
- Keeps production audits secret-safe: env values are never read or printed, only their presence reported (FILLED/EMPTY/ABSENT) with file mtime as supporting evidence, and intrusive checks (docker exec into the app, direct DB queries) are skipped and openly listed as coverage limitations instead of being improvised. Confidence: 0.5
- Validates an externally-meaningful value he supplies against the authoritative external source before it is trusted in configuration: handed over the concrete artefact and asked to check it first ("silahkan periksa dulu dah ini address saya 0xf43f..."), expecting the ground-truth facts fetched live (correct chain, contract vs. plain wallet, activity, balances) to settle a doubt the agent itself raised, rather than taking the value on faith or just re-arguing it. Confidence: 0.45

## Deployment / CI-CD workflow
- Treats a deploy as finished only when verified against independent production evidence, not the CI conclusion alone: the live site's release SHA marker must equal the CI-green commit, the site must answer HTTP 200, and the running containers must use the image digest approved during CI. Confidence: 0.6
- Wants CI/deploy workloads on GitHub-hosted runners, never self-hosted runners on his own low-spec hardware ("spek kentang"): builds, test containers and browser lanes must not compete with his VPS/host for CPU, memory or bandwidth, and keeping that host responsive outranks the convenience of a persistent runner cache. Confidence: 0.65
- When a recent change degrades his environment, prefers restoring the previously working configuration (recovered from git history) over patching forward — e.g. "kembalikan deploy ssh pakai github ci kembali" — while keeping the deploy/release logic itself untouched. Confidence: 0.5
- Deployment gates are repo-scripted and testable — release/redaction/concurrency guard shell scripts each have their own test script that is run locally before pushing. Confidence: 0.5
- Never renames an already-applied migration; a duplicate timestamp prefix is resolved by renaming the later, not-yet-shipped migration (or allowlisting only prefixes already live), after confirming via local DB, migration history, and the current production SHA that it has never been applied anywhere. Confidence: 0.65
- Treats pipeline wall-clock duration as a first-class concern: he reacts with dismay to a slow run ("gila juga 91 menit hanya deploy doang") and expects the agent to measure and report the deploy duration (start/end timing around the watch, run createdAt/updatedAt) — so long CI/deploy times are themselves a defect to be shortened. Confidence: 0.55
- Won't burn a production deploy on work with no functional payload: when a redeploy was dispatched only to carry doc/learning-note commits and re-show the timing, he cut it off ("yaelah jangan redeploy stop aja") and preferred leaving the last healthy release untouched — a redeploy that changes nothing for users should be skipped rather than demonstrated. Confidence: 0.6
- Targets fixes at `main` even while feature work is in flight, with the active feature branch explicitly left untouched — its uncommitted working-tree edits must survive intact ("fixnya di branch main, agar branch ini tidak ganggu"). Expect the work done in an isolated worktree/clone so the in-progress branch is never disturbed, and report back that it is still intact. Confidence: 0.65

## Local dogfood environment
- Verifies UI/behaviour changes in a live local environment instead of trusting the test suite alone: expects the agent to rebuild the Docker stack, point the Telegram test bot's webhook at a fresh ngrok tunnel, and smoke-test the public URL end-to-end so he can look at the running bot himself ("rebuild docker ... setupkan telegram lhistore bot testing nyalakan ngrok agar saya bisa lihat langsung"). Confidence: 0.7
- For UI/visual work, treats "where can I see it" as part of the deliverable: after the change is reported done he asks point-blank where it runs locally ("jalan di localhost mana"), so the agent should proactively hand over the local access URL — and confirm the running server actually serves the freshly built assets — rather than only describing the effect. Confidence: 0.5
- When he does ask for a rebuild ("silahkan rebuild image", "rebuild docker local dan pastikan lhiestore test jalan"), treats it as the full local refresh loop rather than the build alone: rebuild the local image, apply pending migrations explicitly (`docker compose run --rm --no-deps app php artisan migrate --force`, required because the local stack runs with `APP_AUTO_MIGRATE=false`), recreate the containers, then confirm the app is healthy (`/up`), all supervisor workers are RUNNING, and the new schema columns/commands are actually registered — and mention that the image was built from the working tree, so uncommitted changes ride along in it. The requested end state is a verified working local test bot ("pastikan lhiestore test jalan"), so prove it is actually reachable, not only that the containers came up. Confidence: 0.65
- Keeps the local Docker footprint pruned after such runs: unused containers/images/networks/build cache and orphaned anonymous volumes left over from earlier dogfood sessions should be removed to reclaim disk, while the live data volume is left intact. Confidence: 0.55

## Feature scope and cost awareness
- Weighs any new feature or visual addition against over-engineering and the load it puts on his low-spec VPS ("...atau overenginering dan bikin berat vps? menurutmu gimana?"): he wants the agent to say plainly whether an idea is over-engineered and what it actually costs (queries, uploads, storage) before building it, and to recommend the smallest change that reuses existing machinery (a config/asset/one field on an existing pipeline) over per-SKU/per-entity machinery. When the agent lays out the options, he takes the cheapest one that adds no new asset surface — asked to choose between an image-based treatment and a copy-only rework, he picked the text-only polish and dropped the image outright ("kamu ubah aja dah tulisannya perbagus kaya yang kamu sarankan, ga usah pakai gambar"). Confidence: 0.6

## Localization
- Every user-facing string ships in all supported locales (id/en/ms) with identical placeholders, validated by a translation audit test; localized English is the technical default while the product copy stays Indonesian/Malay-flavored. Confidence: 0.65

## Configuration and resilience
- Reserves environment variables for secrets/credentials only: public, non-credential values (e.g. a public RPC endpoint URL) should be pinned directly in code/config so a redeploy is safe without editing `.env` or rebuilding — he questions why such a value lives in ENV at all ("kenapa ga kita hardcode aja kan itu tidak kredensial? ... daripada harus ke env terus rebuild mending di hardcode kalau emang public"), while keeping an ENV override available for the credentialed/paid case. Confidence: 0.7
- Wants calls to an external dependency to survive a single provider being down: a pinned list of several candidate endpoints tried in order with automatic failover on transport/retryable errors, rather than one hardcoded URL — the ENV value stays as the highest-priority entry ("jadi ada fallback aja beberapa rpc"). Confidence: 0.6
