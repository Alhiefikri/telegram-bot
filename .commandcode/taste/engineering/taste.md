# Taste

## Domain and data modelling
- Represents money/state domains as an append-only immutable ledger plus an atomically maintained projection, with a per-source idempotency key and an immutable economic source identity, so replays return the existing result instead of a second effect. Confidence: 0.75
- Treats one service as the sole seam allowed to mutate such state; models elsewhere must not write the balance directly (projection column deliberately not mass assignable). Confidence: 0.7
- Enforces invariants in the database as the final guard — PostgreSQL check constraints (non-negative balance/amount, positive amount) and unique indexes over idempotency/source claims — not only in application code. Confidence: 0.7
- Prefers fail-safe behaviour over fabricated data: when a projection cannot be reconciled with its source of truth, render an explicit localized "unavailable" state rather than a number. Confidence: 0.65
- Keeps automated reconciliation/checking read-only and advisory (a `store-balance:check`-style command that reports mismatches and exits non-zero); never silently repairs state — a repair must be its own explicit, idempotent, audited operation. Confidence: 0.65

- Insists user-visible lists and admin screens be driven dynamically from the real database rather than hardcoded, seeded or guessed data: an admin catalog/icon screen must render the actual `products` rows (each entry configurable individually, e.g. per-product icon) instead of a fixed registry or name-pattern matching, so the display can never show entries that do not exist in the catalog nor hide ones that do — "harusnya ... list product yang udah ada di db bukan random product entah darimana ... jadi dinamis gitu dia. bukan asumsi". Confidence: 0.6

- Expects the registry of editable/capturable slots to have full coverage of the real content it governs: any emoji that actually appears in bot copy (locale JSON + PHP string literals) should map to an editable slot, and a gap he spots by hand (e.g. a receipt emoji, the "back" arrow) is treated as a sample of a class of gaps, not the whole list — he asks for a full scan to find the rest rather than a spot fix ("kamu scan icon mana yang belum masuk ke ... mungkin ada lagi yang belum"), so expect a systematic diff of the registered set against the copy sources, not patching only the reported instances. Confidence: 0.5
- Wants no overlap between parallel registries of editable items: an element that already owns an entry in one list (e.g. an emoji that already has a menu-button slot) must not be re-added to a sibling list (the message text-icon slots) — "jangan ada tumpang tindih, malah memperbanyak icon". Each element should be editable in exactly one list, so a gap-scan must cross-check the sibling registry and exclude anything already owned there before proposing new entries; the correction of an over-broad slot batch was applied as "emojis that already own a menu slot are deliberately absent". Confidence: 0.7

## Code and testing conventions (Laravel/PHP)
- Writes `final` classes with constructor property promotion, explicit return types, enums that carry their own behaviour (`direction()`, `isCredit()`), and model guards that throw on update/delete of immutable rows. Confidence: 0.6
- Tests new concurrency-sensitive behaviour with process-level races (pcntl fork, ready/start markers, result files) behind a dedicated group whose harness refuses to run unless it connects to an isolated test database (`DB_CONNECTION=pgsql`, database name must match test, not production). Confidence: 0.65
- Covers database constraints in tests too: assert that raw inserts violate the expected named constraint. Confidence: 0.55
- Wants implementations and fixes to follow established best practices and be grounded in official library documentation — explicitly asks the agent to "refer context7" (the context7 MCP) for framework/API behaviour instead of ad-hoc patching ("pastikan best practice dan refer context7"), and repeats this ask when greenlighting new feature work ("pastikan best practice dan refer context7" reappears as the condition on a one-line "eksekusi rekomendasimu" go-ahead). Confidence: 0.75
- Expects a fixed defect to be locked down by exhaustive regression coverage of every condition, not just the reproduced case: a data-provider matrix over all relevant provider/system response variants (key missing/nulled/aliased, zero, contradictory aliases, negative/fractional values, HTTP failures, expired/success states, pre-fix stuck rows) plus end-to-end assertions on the money path, justified as preventing recurrence in production. Confidence: 0.75
- Does not trust tests that fake the outbound HTTP/API transport to validate the request body: because the fake accepts any payload, the expected structure is asserted directly (e.g. `reply_markup` must carry an `inline_keyboard` of rows and each row must be a *list* of buttons) through a shared helper instead of `str_contains` on the encoded JSON — a one-level-too-shallow keyboard that the real provider rejects ("expected an Array of InlineKeyboardButton") otherwise sails through the suite. Confidence: 0.5
- Locks a fixed defect down with a regression test over the exact user-visible step that failed (the tap/step immediately after the one already covered), not only on the adjacent steps that were already working. Confidence: 0.5
- Treats non-functional correctness as part of feature sign-off: even after accepting a feature as working ("oke mantap dah bagus"), he asks for one more pass over race conditions, performance issues and N+1 queries ("pastikan sekali lagi mengenai race condition, performance issue, atau N+1 query"). Expect an evidence-backed audit — read-only/transaction-scoped behaviour, index usage, query counts that do not grow with item count, loop-free call paths — rather than verbal reassurance, and permanent guard tests (e.g. query-count assertions) to lock it in. Confidence: 0.7
- When an intentional change alters an already-documented or already-tested behaviour, updates the documentation describing it and the tests that encoded the old behaviour in the same change, keeping each test's original intent (a bounded mutex stays "bounded") rather than deleting or weakening the assertion. Confidence: 0.5
- Keeps cache payloads serialization-safe and reads them defensively: only plain arrays/scalars may be stored (read models are packed into arrays at the cache boundary via an explicit model allowlist and rebuilt on read, because a store that unserializes with `serializable_classes` false hands back `PHP_Incomplete_Class` and fails the reader's typed return), and the read path validates the shape rather than trusting `Cache::remember` — anything that is not the expected array is treated as a miss and rebuilt, so a payload written by an older release can never break a read. Introduces a new design constant for the format boundary (a version key/prefix bumped to invalidate) instead of reusing an existing one, and covers the round-trip plus the serializing-store path with regression tests that must fail without the fix. Confidence: 0.55
- Treats a constant's documented meaning as binding: `DESIGN_VERSION` is scoped to render-design changes, so a payload-format change is invalidated through the cache-key version instead of widening that constant's meaning (reverted `DESIGN_VERSION` back to its original value once the format bump had its own mechanism). Confidence: 0.45

## Production debugging / auditing
- Treats a repeating operational alarm as a defect in the tooling itself: an alert that keeps firing for one unchanged condition ("readinessnya muncul looping gini") counts as a bug to root-cause, not background noise — expect the alert path to be deduplicated per distinct problem (per-fingerprint cache key, persistent cache store, not a short cooldown) and the genuinely recurring residue distinguished from a real loop (per-run job log lines, always-on dashboard badge). Confidence: 0.5
- Diagnoses production-only incidents against live evidence, but strictly read-only: he explicitly asks for a read-only production audit over SSH (host identity/time, deployed commit and working-tree state, memory/disk capacity, running containers, failed units, bounded log windows) and expects nothing on the production host or its data to be changed. He repeats the request when his own change on production did not produce the expected effect ("saya udah set address saya di production tapi masih muncul begitu" → "biar lebih pasti periksa production"), so a mismatch between local analysis and the observed production behaviour must be resolved against the live host — expect the real root cause (e.g. an env key that is absent/never updated on the VPS, a stale container or release state) rather than a restatement of the local findings. He also comes back for a fresh audit after acting on the agent's own cleanup advice — having shut down the non-production `opencode` process on the box himself he immediately asked to re-audit it for what is still consuming it ("saya mau kamu periksa lagi audit ssh production vps nya. apa lagi yang penuh"), so treat this as a repeatable round-based loop: each round must look past the application (Docker image/build accumulation, dev tooling in home directories, journal/apt caches, swap pressure), attribute each consumer to a concrete owner with its size, and hand back a prioritized, permission-gated reclaim plan instead of declaring the host healthy. Each round should also be an explicit before/after diff against the previous audit's figures (disk %, dangling image counts, load, swap): after executing the first reclaim step himself he came back asking what was next and to "bandingkan dengan sekarang", so the report must prove what changed versus the prior round and re-rank the remaining steps. Confidence: 0.7
- Keeps production audits secret-safe: env values are never read or printed, only their presence reported (FILLED/EMPTY/ABSENT) with file mtime as supporting evidence, and intrusive checks (docker exec into the app, direct DB queries) are skipped and openly listed as coverage limitations instead of being improvised. Confidence: 0.5
- Validates an externally-meaningful value he supplies against the authoritative external source before it is trusted in configuration: handed over the concrete artefact and asked to check it first ("silahkan periksa dulu dah ini address saya 0xf43f..."), expecting the ground-truth facts fetched live (correct chain, contract vs. plain wallet, activity, balances) to settle a doubt the agent itself raised, rather than taking the value on faith or just re-arguing it. Confidence: 0.45
- Before greenlighting a destructive/irreversible production cleanup he asks for an explicit, evidence-backed safety verdict rather than trusting the agent's plan is safe ("itu aman kah dihapus docker?"): the answer must state live-verified what is actually removed vs. preserved (running containers and their images untouched, volumes/data never touched), name the safe flag versus the genuinely dangerous one (`docker image prune`/filtered prune vs. `system prune --volumes`), and confirm no running process depends on the target. He triages risk case by case — clearing some items as already safe himself ("kalau hermes mah aman sih") while holding the uncertain one for confirmation — so treat each reclaim action as needing per-target safety reasoning from the agent before it is run. Confidence: 0.5
- Once satisfied on safety he hands over the cleanup as an execution order and expects it done, not re-planned: he asks whether the agent can delete the targets at all and whether anything needs sudo ("KAMU BISA HAPUS KAH APA PERLU SUDO? kalau kamu bisa hapus hapus aja itu jcode sama hermes dahulu"). Expect the agent to separate what it can remove as his own user (home-directory caches/builds) from what is genuinely sudo-gated (journal vacuum, apt clean) and to actually run the non-sudo removals — reporting the reclaimed sizes and what was deliberately kept — instead of returning another approval-gated plan; stop and disable a supervised process properly (systemd/pm2 unit) rather than only killing it so it cannot restart or crash-loop. Confidence: 0.5
- Reports a performance/latency symptom (bot replies late, payment verification slow after a user pays) as a request for a full-stack root-cause diagnosis, not a guess: he asks the agent to inspect the codebase AND audit live production in parallel — code paths, infra/deploy config, data layer, and live host metrics — and to answer explicitly whether the platform has hit its limits ("periksa codebase atau emang udah mentok?"), i.e. whether this is a fixable defect or a hardware/capacity ceiling. Expect the ranked bottlenecks each backed by code (file:line) or production-log/metric evidence, his own candidate cause (here "PHP is slow" / the frontend+backend monorepo) confirmed or refuted with evidence, and a prioritized fix plan. Confidence: 0.5
- For a live outage he caused himself (bot stuck/wedged after he enabled a new feature — custom emoji on product buttons — so users can no longer see products), asks for a fast parallel path: a quick root-cause diagnosis AND an immediate kill-switch, i.e. disable the offending feature so the bot runs normally again ("analisis cepat mungkin atau matiin dulu custom emoji ... biar bot bisa jalan normal"). Expect service restoration offered up front alongside the diagnosis, not a long investigation that leaves the bot broken. He keeps pushing the same restore-first instinct even after the fix exists: asked to remove the custom icon he had just added and roll it back to the repo default, clearing its registry cache, purely to unblock faster ("hapus dulu icon yang baru saya masukin balikin ke default. biar cepat masalahnya") — so execute the revert he asks for even when the agent's own evidence says it is not the root cause, delivering it as a separate measure while keeping the real diagnosis and its proof intact. Confidence: 0.55
- Wants a shared root cause's blast radius spelled out, not just the first symptom: right after a root cause is fixed he asks whether the impact was limited to the named feature or broader ("itu cuma sales prooff aja kah?"), cross-checking it against one of his own symptoms that is still broken (fake notification from the dashboard "kok belum bisa ya?"). Expect the diagnosis to enumerate every user-visible path that depends on the same root cause and confirm each one against live production state (including whether the fix is actually deployed there yet) rather than only the path originally reported. Confidence: 0.5
- Names the workflow he wants run, not only the symptom: for a production incident he says "lakukan bug fixing skill", so expect the repo's dedicated diagnosing-bugs skill to frame the whole investigation — systematic recon (context doc + recent commit diffs), a strictly read-only production feedback loop, ranked falsifiable hypotheses, minimal reproduction, then the fix placed at the true seam with a red-capable regression test and a post-mortem — rather than ad-hoc poking at logs. Incident reports are terse and symptom-first, and he may bundle one confirmed symptom with a second hedged guess in the same breath ("...mungkin juga ketika saya mau tambah stok product tidak muncul"), expecting both investigated as potentially a single shared root cause. Confidence: 0.5

## Deployment / CI-CD workflow
- Treats a deploy as finished only when verified against independent production evidence, not the CI conclusion alone: the live site's release SHA marker must equal the CI-green commit, the site must answer HTTP 200, and the running containers must use the image digest approved during CI. Confidence: 0.6
- Wants CI/deploy workloads on GitHub-hosted runners, never self-hosted runners on his own low-spec hardware ("spek kentang"): builds, test containers and browser lanes must not compete with his VPS/host for CPU, memory or bandwidth, and keeping that host responsive outranks the convenience of a persistent runner cache. Confidence: 0.65
- When a recent change degrades his environment, prefers restoring the previously working configuration (recovered from git history) over patching forward — e.g. "kembalikan deploy ssh pakai github ci kembali" — while keeping the deploy/release logic itself untouched. Confidence: 0.5
- Deployment gates are repo-scripted and testable — release/redaction/concurrency guard shell scripts each have their own test script that is run locally before pushing. Confidence: 0.5
- Never renames an already-applied migration; a duplicate timestamp prefix is resolved by renaming the later, not-yet-shipped migration (or allowlisting only prefixes already live), after confirming via local DB, migration history, and the current production SHA that it has never been applied anywhere. Confidence: 0.65
- Treats pipeline wall-clock duration as a first-class concern: he reacts with dismay to a slow run ("gila juga 91 menit hanya deploy doang") and expects the agent to measure and report the deploy duration (start/end timing around the watch, run createdAt/updatedAt) — so long CI/deploy times are themselves a defect to be shortened. Confidence: 0.55
- Won't burn a production deploy on work with no functional payload: when a redeploy was dispatched only to carry doc/learning-note commits and re-show the timing, he cut it off ("yaelah jangan redeploy stop aja") and preferred leaving the last healthy release untouched — a redeploy that changes nothing for users should be skipped rather than demonstrated. Confidence: 0.6
- Weighs deploying a CI-green fix immediately against batching it with upcoming feature work, and asks the agent to judge the urgency for him ("apa urgent deploy sekarang atau jika saya mau tambah feature atau perbaikan feature apakah nanti sekalian aja?"). Expect the trade-offs spelled out — small marginal deploy cost and a cooler DB if shipped now, versus cleaner rollback attribution and fewer gate-flaky deploy attempts if the fix and the feature are reviewed together — plus a recommendation that also warns against parking the fix for weeks. Confidence: 0.45
- Targets fixes at `main` even while feature work is in flight, with the active feature branch explicitly left untouched — its uncommitted working-tree edits must survive intact ("fixnya di branch main, agar branch ini tidak ganggu"). Expect the work done in an isolated worktree/clone so the in-progress branch is never disturbed, and report back that it is still intact. Confidence: 0.65
- Gates the production deploy on behavioural verification of every affected user-visible flow first, not just a green suite: when the fix is ready he says "verifikasi dulu ... jika memang udah di fix silahkan deploy prod" (the go-ahead is conditional on the proof), naming the flows that must be confirmed restored to their old behaviour ("usahakan kaya sebelumnya") — fake sales-proof notification, real sales proof, stock-added and stock-out channel notifications. Expect the pre-deploy check to exercise each of those paths end-to-end (ideally against the candidate image / real data, read-only) and report per-flow results, then dispatch the deploy only once all pass. Confidence: 0.55

## Local dogfood environment
- Verifies UI/behaviour changes in a live local environment instead of trusting the test suite alone: expects the agent to rebuild the Docker stack, point the Telegram test bot's webhook at a fresh ngrok tunnel, and smoke-test the public URL end-to-end so he can look at the running bot himself ("rebuild docker ... setupkan telegram lhistore bot testing nyalakan ngrok agar saya bisa lihat langsung"). Confidence: 0.7
- For UI/visual work, treats "where can I see it" as part of the deliverable: after the change is reported done he asks point-blank where it runs locally ("jalan di localhost mana"), so the agent should proactively hand over the local access URL — and confirm the running server actually serves the freshly built assets — rather than only describing the effect. Confidence: 0.5
- When he does ask for a rebuild ("silahkan rebuild image", "rebuild docker local dan pastikan lhiestore test jalan"), treats it as the full local refresh loop rather than the build alone: rebuild the local image, apply pending migrations explicitly (`docker compose run --rm --no-deps app php artisan migrate --force`, required because the local stack runs with `APP_AUTO_MIGRATE=false`), recreate the containers, then confirm the app is healthy (`/up`), all supervisor workers are RUNNING, and the new schema columns/commands are actually registered — and mention that the image was built from the working tree, so uncommitted changes ride along in it. The requested end state is a verified working local test bot ("pastikan lhiestore test jalan"), so prove it is actually reachable, not only that the containers came up. Confidence: 0.65
- Keeps the local Docker footprint pruned after such runs: unused containers/images/networks/build cache and orphaned anonymous volumes left over from earlier dogfood sessions should be removed to reclaim disk, while the live data volume is left intact. Confidence: 0.55
- Names the tunnel tool himself and picks ngrok rather than the cloudflared setup the repo defaults to ("PAKAI NGROK AJA TUNNELNYA"): treat ngrok as the tunnel for exposing the local test bot, keep the local web port matched to the tunnel's target port, and note that a recreate can silently move the container off that port if `WEB_PORT` differs from the tunnel. Confidence: 0.4
- To eyeball a feature that is gated behind readiness/config, he authorises seeding the local database with dummy rows so the surface actually becomes reachable ("tambahkan binance dana address usdt dummy di db agar aktif mereka berdua saya mau lihat icon nya apakah terapply apa tidak"): placeholder settings/receiver rows (a fake wallet address, official token contract, `verified`/`active`) are acceptable in the local stack purely to unlock the screen, and the fact that the data is dummy belongs in the report as an explicit "local only, never in production" caveat rather than a reason to refuse. Expect the deliverable to be the real rendered outcome (the buttons with their applied icons), not just "the flag is now true". Confidence: 0.5
- Treats a change as delivered only once the *running* environment actually executes it, not when the source/working tree is fixed: when the agent reports before/after numbers but notes the image was never rebuilt, he catches it ("ow berarti belum di rebuild ya") and immediately orders the rebuild so he can judge it himself ("silahkan di rebuild agar saya bisa lihat"). This matters because measurements must come from the rebuilt artifact/container rather than the host tree (a host-tree benchmark can even look slower until the container is timed warm). He states acceptance of an optimization as two conditions held together — measurably lighter AND existing behaviour unbroken ("apakah memang udah ringan dan tanpa merusak icon") — so an optimization is not counted done until the rebuilt runtime proves both the improvement and zero regression. Confidence: 0.55

## Feature scope and cost awareness
- Weighs any new feature or visual addition against over-engineering and the load it puts on his low-spec VPS ("...atau overenginering dan bikin berat vps? menurutmu gimana?"): he wants the agent to say plainly whether an idea is over-engineered and what it actually costs (queries, uploads, storage) before building it, and to recommend the smallest change that reuses existing machinery (a config/asset/one field on an existing pipeline) over per-SKU/per-entity machinery. When the agent lays out the options, he takes the cheapest one that adds no new asset surface — asked to choose between an image-based treatment and a copy-only rework, he picked the text-only polish and dropped the image outright ("kamu ubah aja dah tulisannya perbagus kaya yang kamu sarankan, ga usah pakai gambar"). Confidence: 0.6
- Judges feature scope by real usage but always against change risk: he first ordered the entire Product Category feature deleted — model, admin CRUD, filters, routes, tests, locale keys and docs — because "kategori itu terlalu ribet saya ga pernah setting btw. makanya sayang featurenya ga ke pake", collapsing the catalog to the two concepts he does use (family + variant) and choosing that over keeping both. He then withdrew the deletion once he saw how much would be sacrificed, keeping the feature and narrowing the ask to the two safe changes ("banyak yang dikorbankan takutnya jadi tambah bug saya rasa tetap aja pakai kategori jadi permintaan saya cuma 2 aja. permintaan 3 di hapus"). So a wide deletion is not authorized by "unused" alone: produce a complete removal inventory and an honest blast-radius/regression-risk assessment, prefer keeping a working feature over a broad removal that could introduce new bugs, and when he trims a request down still deliver the retained items in full. Confidence: 0.6
- States his design goal as "simple but dynamic" together — simplicity of the model does not excuse hardcoded/static data, and dynamic-from-the-database does not excuse extra concepts or steps; a display attribute should be *derived* from the real records (a variant's icon follows its family's logo dynamically) rather than stored/guessed per item. Reconfirmed when the product-detail screen fell back to the default glyph instead of the family's captured icon and he reported it as a bug to fix ("fix juga bagian ini di checkout detail bukannya pakai icon family malah pake icon default"). Confidence: 0.6

## Localization
- Every user-facing string ships in all supported locales (id/en/ms) with identical placeholders, validated by a translation audit test; localized English is the technical default while the product copy stays Indonesian/Malay-flavored. Confidence: 0.65

## Performance and capacity program
- Treats the VPS hardware sizing as frozen and off the table: a capacity upgrade is explicitly ruled out ("update kapasitas vps itu udah ga mungkin lagi karena saya mau tetap seperti ini"), so any performance plan must assume the fixed 2 vCPU / 1.9GB / 40GB box and work by reducing load and reclaiming already-present resources (pruning images, removing non-production processes, tighter FPM/Postgres/Redis budgets) rather than recommending more hardware or an extra host for the app. Confidence: 0.8
- Treats performance work as an ongoing program, not a closed ticket: right after a batch of fixes lands and is reported, he asks for the next step of the roadmap he remembers the agent planned ("lalu langkah selanjutnya apa nih yang tadi kamu planingkan agar optimasi arsitektur dan vps makin kenceng dan ga delay lagi") — so the earlier plan must be carried forward, refreshed with data from the just-shipped change, and re-ranked by impact vs. risk instead of starting over. He expects the costlier/decisive items (capacity upgrade, moving cache/session/queue/lock to Redis, Postgres tuning) to be split out from the free, low-risk cleanups he can approve immediately, each with the reason it is needed. Confidence: 0.5
- Recurring concern is latency and VPS capacity: he frames the goal as "makin kenceng dan ga delay lagi", so optimizations are judged by whether they remove the slowdowns (sweep/scan duration, DB CPU saturation, polling I/O) and by what they add to his low-spec host — report the measured before/after and the resource cost, not just the architectural elegance. Confidence: 0.5

## Configuration and resilience
- Reserves environment variables for secrets/credentials only: public, non-credential values (e.g. a public RPC endpoint URL) should be pinned directly in code/config so a redeploy is safe without editing `.env` or rebuilding — he questions why such a value lives in ENV at all ("kenapa ga kita hardcode aja kan itu tidak kredensial? ... daripada harus ke env terus rebuild mending di hardcode kalau emang public"), while keeping an ENV override available for the credentialed/paid case. Confidence: 0.7
- Does not want a user-facing value silently derived from a provider response and stored as if the owner had chosen it: auto-filling a product's text emoji from the plain Unicode base returned for the captured premium sticker put an unrelated emoji (the pack's base glyph) in front of customers. Prefers an explicit owner input per layer instead — the same bot capture screen accepts a premium emoji for the button icon and a plain Unicode emoji for the text icon, with the pre-existing dashboard field demoted to a fallback — and rejects the intermediate "derive one field from the other" design once the outcome is visible. Confidence: 0.5

Confidence: 0.6
