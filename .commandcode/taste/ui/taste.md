# Taste — UI / presentation

- Prefers compact list layouts with no wasted whitespace: entries should sit close together in a tight, scannable block ("jangan dibuat space terlalu lebar"), but with a small deliberate gap so they are not fully glued together ("berdempet tapi jangan terlalu dempet") — wide, airy spacing between rows reads as a defect. Confidence: 0.7
- Expects unavailable/sold-out items to be visually and functionally unambiguous: the action button turns red and is not clickable, and the "Sold out" label is paired with a red icon (e.g. a red ✕) right next to the text. Confidence: 0.7
- Prefers Telegram inline keyboard action buttons in blue (`style primary`) rather than green (`style success`), treating green as generic/cheap ("hijau pasaran banget tombolnya") and blue as carrying a premium feel ("kalau biru itu ada rasa premium") — the "premium" cachet of the accent colour is a stated reason to pick it, not just consistency. He still keeps red (`style danger`) for the sold-out/unavailable case, so colour keeps its status meaning (available=tinted accent, out-of-stock=red) while the positive colour shifts from green to blue. Confidence: 0.55
- Drives UI review by pasting the current rendered output (e.g. the Telegram message text as the user sees it) and asking for a redesign with the desired state described in prose, rather than pointing at code or naming components. Confidence: 0.55
- Treats buyer-facing copy as his to proofread: before changes, he asks for the exact message-by-message experience the user gets ("pesan apa yang muncul setelah saya klik ... biar saya koreksi jika salah") and expects the agent to reconstruct the real strings verbatim — each screen's text plus the button labels and follow-up prompts, sourced from the actual renderer and locale files, not a paraphrase or a code summary — so he can correct the wording himself. Confidence: 0.5
- Wants visual consistency across surfaces and treats an already-working element as the golden reference: an existing presentation treatment should be reused for equivalent content elsewhere, pointed out by naming the reference ("di bungkus quote sama seperti product details") rather than describing the styling from scratch, and when reporting a bug he names the correct equivalent the broken surface must match ("pastikan dia sama kaya tombol varinat nya") instead of specifying the fix himself. Within a single view, an emoji he never chose must not appear next to the premium/custom emoji for the same item — he filed the auto-filled plain glyph as a bug ("ketika saya set emoji custom tapi malah keyboard emoji aslinya yang keluar") because the text showed a competing plain emoji while the button showed the captured premium one. But deleting the text icon is not an acceptable fix either: when the agent's follow-up stripped the emoji out of every catalog message he reported that as a new, equally terse bug ("kenapa malah ngilang sih?"), so downstream the same commit path was reworked rather than kept. The resolution he wants is control, not removal: the plain text emoji stays visible next to the premium button and he sets it himself from the bot, i.e. a fix must correct the wrong value instead of deleting the element (a disappearing element reads as a regression, even when the suite and docs were updated to bless it). Confidence: 0.6
- Treats consistency itself as a standalone, worth-doing task — he greenlights it in one terse line ("oke silahkan buat konsistensi. lalu comit push.") and expects the canonical treatment to win everywhere, including the channel/post copy vocabulary (one emoji per concept, e.g. 📦 for stock in both the restock and sold-out posts) and locale files that drifted from the en/id wording. Cosmetic unification is not "nice to have" for him; it ships with the same commit/push + tests close as functional work. Confidence: 0.55
- Verifies the reach of a new customisable presentation feature rather than assuming it: when icons became configurable for catalog family/product buttons he immediately checked whether the same treatment covers every button in the bot ("udah support saya ganti semua kan? bukan hanya family dan produc icon?"), treating "only some surfaces" as incomplete and greenlighting the expansion to the shared navigation rows — expect to state the exact coverage (what is covered, what is explicitly not) and to offer extending the same seam to the remaining button groups. Confidence: 0.5
- Sets explicit, numeric minimums for paginated lists instead of leaving page size to the implementer (product list pages must show at least 15 items). Confidence: 0.55
- Treats catalog/list length as a UX constraint alongside spacing: he is wary of a design that makes the product list longer down the screen ("yang saya takutkan kalau hanya 1 variant dia bakalan panjang list produk kebawah") and prefers each entry to stay one compact line rather than a single item breaking into a multi-line block — surface list-length growth as a cost when proposing a change. Confidence: 0.5
- Wants Telegram message/caption copy annotated with emojis for visual appeal ("ada beberapa emote biar enak di pandang"), and frames it as consistency rather than decoration — a plain block of label:value lines reads as unfinished. Confidence: 0.55
- Wants concise, context-local back navigation: a back button should return to the nearest related list (the product family's variant list) rather than a broader browse/product list, and he will restructure the flow to remove redundant navigation modes if that is what "ringkas" requires ("jangan balik ke daftar product mode kategori. tapi langsung ke list family jadi lebih ringkas"). Confidence: 0.5
- Likes buyer-facing copy to carry a scarcity/stock signal (telling the customer how much stock is left) as part of making the post appealing — states it as his own design plan and expects the agent to weigh it rather than silently drop it; he keeps pursuing the idea even after the agent argues against it ("kira kira misalnya kita tambahin 1 lagi yaitu sisa stock produk itu jadinya gimana?"), so treat it as an open design question to render and re-argue rather than a dismissed one. Confidence: 0.55
- Keeps public buyer-facing copy compact by dropping internal/administrative detail rather than explaining it: told to either shorten the provider/admin fee reference or remove it entirely, he chose "no need to be told at all" — the difference between subtotal and amount paid is left implicit in the caption because the attached invoice image already itemizes the fee. Confidence: 0.55
- Points at a live external website as the styling/motion benchmark instead of specifying the effect himself ("tambahkan sedikit animasi sama seperti website marketku.id"): the named site is the source of truth for the visual language, so expect the agent to study its actual CSS/keyframes/hover rules and translate that motion vocabulary into the existing storefront rather than inventing generic animations. The ask is framed as incremental polish ("sedikit"), so ramp up the existing UI with subtle motion rather than rebuilding the design. Confidence: 0.5
- Accepted the scarcity signal as a conditional, low-stock-only line (a "🔥 Only N left in stock" style hint rendered only while a few units remain, and silent at zero or for multi-item posts) rather than a permanent stock number burned into the frozen caption — after seeing that rendering he greenlit the narrower version for implementation. Confidence: 0.6
- Specifies a desired UI by pasting a screenshot of the target look from another bot/product and asking for the same ("saya mau biar ada custom tombol begini" + image), rather than describing the styling in words — treat the reference image as the spec and first work out which visual elements actually compose it (e.g. brand logos that are Telegram custom emoji rather than plain Unicode emoji) before implementing. Confidence: 0.45
- Expects every actionable button to carry an icon, and reports icon-less buttons in the same breath as buttons showing the wrong icon ("... itu masih default bahkan ada yang ga ada icon"): a button that ships as bare text is a defect just like a wrong glyph, so a new action must get a sensible default emoji (💎 for Binance Pay ID, ⛓️ for USDT BEP20) plus an editable slot when the glyph is new. Confidence: 0.55
- Treats a configured icon that does not visibly take effect as a bug on the surface he is looking at, not as a saved setting: after the slots were "set" he listed the specific buttons still rendering the default glyph (Statistik, Ikon Produk, Masukkan jumlah kustom, QRIS, USDT, Saldo) and expected the captured premium emoji to appear there too — the icon layer must cover inline keyboard **button** labels (rendered through `icon_custom_emoji_id`, since Telegram ignores markup inside button text), not only message bodies and captions. Confidence: 0.6
- Wants one configured icon per concept applied everywhere that concept appears, rather than per-surface configuration: once the menu's Saldo icon is set, the same emoji used by unrelated buttons (the payment-method and product-detail "Saldo" button) must follow that configured icon instead of staying the plain glyph, so a single setting propagates and he is never asked to set the same icon in a second list. Confidence: 0.5
- Wants admin/editor list screens to *preview* the value that was actually configured, rendered exactly as the customer sees it through the same mechanism as the live surface — not the untouched default. When a slot has a captured premium emoji, the icon-edit list must render that premium emoji (via `icon_custom_emoji_id`, the same shape catalog buttons use) so an edited slot visibly differs from an unedited one that keeps its fallback glyph; showing the stock/fallback icon after a change reads as "still using the default" even though the value was saved ("kan harusnya kalau udah di ubah ada previewnya gitu bukan pake icon bawaan"). Confidence: 0.5
- Prefers appearance to be configured at the aggregate/parent level with children inheriting it, so the settings list stays short: for the "Ikon Produk" admin list he explicitly asked to switch from per-product entries to per-family ("lebih bagus setting per family aja"), showing the family name once instead of one row per variant ("chatgpt punya 2 varian, cukup tulis nama family-nya aja") and having every variant follow the parent icon when set — fewer configurable rows is the stated goal ("jadi makin dikit listnya"), and the length of a configuration list is treated as a UX cost in its own right. Confidence: 0.65
- Judges the look of a notification/copy by receiving it as a real delivered message in his own bot rather than reading it in chat: asked for the stock-added and stock-out ("info product nambah dan habis") notifications to be sent to his bot so he could decide whether they look good ("coba kirim ke bot saya mau lihat apakah bagus apa tidak") — treat cosmetic sign-off on buyer/admin-facing messages as requiring the actual pushed rendering he can see, then await his verdict rather than treating the copy as approved. Confidence: 0.5
- Treats two conceptually distinct things sharing one icon/slot as a defect: he reported that Binance Pay ID rendered the same icon as USDT BEP20 (BSC) *and* that Binance had no own entry in the text-icon list, so distinct payment rails/brands each need their own differentiable glyph and their own editable slot rather than aliasing onto one shared "crypto" slot — a collision is wrong even when both buttons technically show an icon. Confidence: 0.55
