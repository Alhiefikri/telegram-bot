# Taste
- Follows a complete end-of-task loop for verified fixes: commit the change, push to the main branch, then close the related issue (with a summary comment) — all in one go, without waiting for a separate reminder to close the issue. Explicitly prompts the agent to do this when ready, repeating the instruction even if the work already finished ("silahkan commit dan push lalu close issue terkait", "oke silahkan commit dan close issue terkait") and expects the agent to verify state and report back if nothing is left. Confidence: 0.9
- "Commit dan push" means sweeping in everything outstanding, not just the change just finished: carried-over working-tree edits from earlier local sessions, docs, migrations and agent learning notes all get staged and committed, and he explicitly asks that nothing be left behind ("pastikan tidak ada yang tertinggal", "commit push. semua perubahan") — expect to show proof of a clean tree (branch in sync with the remote, zero modified/untracked files) in the closing report, including carried-over pending notes he knows about. Confidence: 0.7
- Keeps production deployment out of the routine task loop: commit/push only trigger CI, and deploy stays an explicit manual dispatch ("jangan deploy", "commit push aja jangan deploy prod", "jangan deploy dulu") — but when the user does ask for it, the redeploy is the closing step of the loop ("...dan redeploy kembali"). He also deliberately separates deploy from the change/commit session, planning to run prod deployment in a later session ("nanti setelah ini saya akan deploy prod di next session. bukan di sini"), so a commit/push task should end at the pushed-and-CI-verified state and stop there — and the closing report should prove no production deploy run was triggered. Confidence: 0.75
- Wants a red CI/CD pipeline driven to green autonomously in one session: diagnose the failure, fix the root cause, verify the CI-equivalent checks locally, commit/push, re-run the pipeline until it passes, then redeploy and confirm the live release matches — without pausing for confirmation between steps ("jalankan workflow ci/cd looping sampai selesai fix jika ada masalah dan redeploy kembali"). Confidence: 0.8
- Expects the fix pass to clear every blocker, not just the first failure, across the whole commit → CI → deploy path: latent issues that would break the next CI job (e.g. formatter/style violations hiding behind an earlier failing step) get fixed in the same pass so CI goes green in one push, and his "fix jika ada error dan redeploy" also authorizes diagnosing and fixing a failed production deploy — including when the blocker is a pre-existing bug in the repo's own release-gate/ops tooling — adding regression tests before re-dispatching the deploy. Confidence: 0.6
- Communicates in Bahasa Indonesia (Indonesian); expects the agent to respond in Indonesian as well. Confidence: 0.9
- Often opens with his own hypothesis about a failure ("kayanya karena ...") and asks for analysis ("coba analissi") — expects the agent to investigate it against live evidence, quietly correct the premise when the evidence contradicts it, and say plainly what the real cause was, not just comply with the proposed fix. Confidence: 0.6
- Reporting a defect doubles as a design-review request: alongside the fix he asks for criticism of the surrounding flow because it "feels convoluted" and "not like bots/products generally" ("saya mau kamu berikan kritik karena logic atau flow ... itu saya rasa agak ribet ... tidak seperti bot pada umumnya"), expecting the agent to state the root cause, then name the structurally weak points (manual steps, missing notifications, no self-service path, duplicated state logic) and close with concrete recommendations ranked by priority — not just deliver the patch and stop. Confidence: 0.6
- Steers sessions with terse prompts ("oke silahkan commit dan push lalu close issue terkait", "/cmd -yolo", "resume", "continue") and expects the agent to work autonomously through the full task loop without intermediate check-ins. Confidence: 0.65
- Monitors long-running work and reads prolonged silence as a stall: mid-task he checks in with a bare "stuck kah" ("are you stuck?") while the agent is grinding through multi-minute background verification loops, so an extended stretch of tool activity with no visible explanation can look like a hang — surface interim progress (what is currently running, why, and any partial findings so far) during long background loops/suite runs rather than going quiet until the final report. Confidence: 0.5
- When asked to explain an issue ("masalahnya apa sih, coba jelasin", "jelasin ke saya kenapa itu terjadi dan apa perbaikan kamu"), prefers a plain-language walkthrough — root cause first, then the consequences (with concrete real-world impact), then the fix — using short, structured sections and avoiding jargon, rather than a purely technical changelog recap. He asks for the "why" even after the fix has already been reported as done — re-asking what caused the failure and restating his intent tersely when an earlier answer missed the point — so a delivered fix still owes him a plain-language explanation of the cause. Confidence: 0.65
- After a substantial change lands, asks for the resulting end-to-end flow rather than the diff ("coba jelaskan ke saya sekarang flownya gimana"): expects a structured, numbered walkthrough of the whole system path — entry points, each stage's behaviour, edge cases, and the race/ordering guarantees — closing with a "what this means in practice" summary. He wants to understand the current system state as a story (customer → system → operator), not a technical changelog of what was edited. A completed, evidence-backed feature report can still leave him unsure of the practical steps ("jadi gimana nantinya saya masih bingung"), and then he wants a second, from-zero operational walkthrough: the problem stated in one plain sentence first, then the numbered stages, each stage split by who acts (his own manual one-off setup vs. what runs automatically vs. what the end user never has to do), plus a short "if something looks wrong" section with the concrete recovery command — and an offer to take over the most tedious manual part. Confidence: 0.5
- Can request a second, simpler layer of the same explanation for a non-technical audience ("jelasin ke orang awam"), expecting an everyday analogy (e.g. the bug as a cashier forgetting the backup plan), a plain "what this means for me" consequence, and its own short "what to know" section — delivered as a fresh standalone write-up, in context of the same issue and next-step question. Confidence: 0.5
- Re-reports a defect that was already reported as fixed as a bare user-visible symptom in a short, frustrated message ("MASIH BUG ... klik tombol icon nya ga terjadi apa apa"), treating the earlier fix plus a green suite/CI as no evidence at all: expects a fresh root cause dug out of live runtime data (the stored update rows, the provider's real API error text) and proof by replaying the exact failing path end to end, not a restatement of what was already fixed. Confidence: 0.5
- Treats verification as part of the task, not optional: before committing, run the whole test suite (`php artisan test`), the formatter in check mode (`./vendor/bin/pint --test`), and the heavyweight PostgreSQL concurrency gate (`composer test:concurrency-gate`) — each configured via env vars/artefact dirs — and report the pass counts as evidence. Confidence: 0.7
- Keeps a documented domain model: introducing a new domain concept means updating the `CONTEXT.md` glossary (including an "_Avoid_:" list of rejected synonyms), the `docs/agents/codebase.md` map/table/test index, and adding a numbered ADR under `docs/adr/`. Confidence: 0.65
- Treats production data remediation as part of a fix when the affected rows came from his own prod testing rather than real users: he authorises deleting the impacted production records outright ("biar yang udah pernah hit gapapa di hapusin aja, soalnya ini baru saya test di prod") alongside the code change. The same applies to configuration he added while experimenting on production: reverting a custom emoji to the code default and purging its cache is requested as a quick first-aid step ("hapus dulu icon yang baru saya masukin balikin ke default"), and he is fine with the agent performing that production write itself — direct DB update plus cache invalidation on the live host — rather than routing the revert through a deploy. Confidence: 0.6
